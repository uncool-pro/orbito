# Changelog

How to update a project: `npm run update` in the project (or `/orbito-update` in Claude Code). It pulls the newest Orbito and refreshes the skills, agents and commands in `.claude/`; your screens, flows and design system are never changed. Entries marked **template** add something to new projects only: ask Orbito to bring it into an existing one.

## 0.9.61 — not released yet (MVP to test with people)
What the board shows next to a screen, a mode for whoever builds it, and phones of every size. A version to try with users before 1.0.
- **Comments on screens, as changes with a status.** Write what should change on a screen, in its details or next to it in the prototype (the board shows how many wait above each screen). Each comment is `open`, `doing` or `done`; Claude moves it along as it makes the change and notes what it did, and `/orbito-comments` has it go through all open ones. They live in `comments/<screen-id>.md`, one file per screen, so they travel through git with the mockups and two people rarely touch the same file. Works in Docker as well: `comments/` is the one folder the board may write.
- **Changed: Orbito's interface is in English only.** `locale` in `orbito.config.ts` is now the language of the product: what the mockups are written in (any language, e.g. `pl` or `de`) and the `lang` of an exported page. **What to do:** nothing; a project with `locale: 'pl'` keeps Polish mockups and gets the interface in English.
- **The design-system catalog, rearranged** the way Material, the Human Interface Guidelines and Storybook show a design system: the overview has the foundations (colour, type, spacing…) as small pictures and a live gallery of the components; a component page leads with the component itself, large, then its variants, how to use it (do and don't) and where it is used; each token group reads as one table.
- **The left panel as in Figma:** the pages in a small list of their own on top, the features of the page under it, each opening into its screens. A second click on the open feature shows the whole page again; "All flows" is gone.
- **Requirements with their text.** A screen's details show its stories from `requirements/*.md` (the tracker's local mirror): the title, the status, and the story with its acceptance criteria under it. A screen with no ids of its own shows its feature's. In Docker the renderer now reads `requirements/` (read-only).
- **Ways out, sorted.** The details list the screens of the same feature; the ones in other features fold into one line ("→ 3 screens in 3 other features"), and the menu most screens repeat (a tab bar) is named once.
- **Dev mode.** A "Dev" switch in the top bar. The right panel then shows the selected screen's code and the code of each component it uses, with a copy button and a width you drag; the prototype shows the file's path above the screen (copy it, or open it in VS Code) and measures like Figma: hover for the size and the distances to the edges, click an element and hover another for the distance between them, named by the spacing token when one fits. While dev mode is on, a click measures instead of navigating.
- **Phones of every size.** A phone screen in the prototype switches between a small phone (iPhone SE, 375 × 667), its own size and a large one (Pro Max, 430 × 932).
- **The page as features.** The flows view of a whole page can switch from screens to features: one box per feature, arrows with the number of links between features, the menu left out. A click opens the feature.
- **Changed: a click on a screen on the board shows its details.** It selects the screen and opens the right panel (its code in dev mode), the same in every mode. The prototype starts from **▶** above the screen, with a **double click**, or from the island. **What to do:** nothing in your project; where you clicked a screen to try it, use ▶ or a double click.
- **Dev mode on the board:** hovering a screen measures it too, in the design's own pixels.
- **Docker:** compose passes the project folder on your computer to the board (`ORBITO_HOST_ROOT`), so dev mode copies real paths there too. **What to do:** update as DOCKER.md says ("Update"); the update writes the new `compose.yaml` and adds `comments/` and `requirements/` to the project.

## 0.9.6 — not released yet
Fixes from the first independent review of the code, and tests that click through the board, a new project and the container.
- **Fix: names with spaces or Polish letters.** A page or flow named that way could send the board into a redirect loop, and a malformed address broke the page. Neither happens now.
- **Fix: an update applies on the first run.** After `orbito update --pull`, the version just downloaded finishes the update, so its changes no longer wait for a second run.
- **Docker:** `docker compose run --rm export <screen-id>` takes the screen directly, and every folder `compose.yaml` mounts now exists in the project.
- **Without git:** a folder downloaded as a ZIP now explains how to update it.
- **Fix: the first update no longer removes a skill of yours.** A new project had no list of what Orbito installed until its first update, so a skill of yours named like one Orbito retired (for example `landing-page`) was deleted with no copy. New projects now have the list from the start, and in an older project without it such a skill is saved to `.orbito/backup/` first and listed in the output.
- **Fix: a click on a status no longer wipes the other statuses.** When `.orbito/status.json` could not be read, for example after a merge conflict, saving a status replaced the whole file. Now nothing is written and the board tells you to fix the file.
- **Fix: one broken file no longer leaves an empty page.** A screen or flow file that throws while loading, an unknown viewport, a page without flows or an unknown language now show up as problems in the top bar, and the rest of the board keeps working. Screens now load one by one, so `npm run build` makes one small file per screen.
- **Changed: the spacing rule works for values written as text.** `padding: '8px 0'` used to pass `check:ds` by mistake. **What to do:** run `npm run check:ds`; you may see new `raw-spacing` warnings, and with `--strict` they fail the check. Use a `var(--space-…)` token, or mark a deliberate one-off with `// ds-exception: <why>`.

## 0.9.5 — 2026-10-29
Security fixes from the first security audit of Orbito (dependencies were clean: no known vulnerabilities, no telemetry), and a full-size prototype for responsive pages.
- **Changed: a responsive page shows one size at a time in the prototype.** A screen with `viewports` (e.g. a landing page) used to show all its sizes side by side, each one small. Now the prototype shows one size, as big as the window allows, and a **Desktop / Tablet / Mobile** switch in the top right corner changes it; the size you pick stays while you click through and after a reload. Nothing to change in your project. The look & feel and landing-page skills tell Claude to check all three sizes and point you to the switch.
- **`npx --no orbito` everywhere:** skills and docs ran `npx orbito …`. The name `orbito` on npm belongs to someone else, so without Orbito installed locally `npx` could offer to download and run that package. `--no` never downloads anything: inside a project it runs Orbito's CLI, outside one it refuses.
- **The dev server refuses requests from other sites:** a page from another site open in the same browser could send requests to the board's local endpoints (for example write a note into `status.json`, which Claude reads, or open the file manager). Requests from other sites now get 403; the board and the command line work as before.
- **Materials are data, never instructions:** the skills that read `raw/` and other material people bring now say so explicitly — commands written inside a document or a page are not followed, flagged as suspicious, and nothing is sent anywhere or run because a material suggests it.
- **`orbito export` never cleans a folder it did not make:** `--out` pointing at a folder with work in it (e.g. `screens`) used to empty it first; now the export only cleans an empty folder or its own (marked with `.orbito-export`), otherwise it stops.
- **`.env` is ignored by git** in new projects, so keys for connected tools are not committed by accident.

## 0.9.4 — 2026-10-26
- **Fix: a click on a screen opens the prototype again.** The board took the pointer on every press, and some browsers then delivered the click to the board instead of the screen, so nothing opened. The pointer is now taken only when a drag starts, and a click is resolved by what is under the cursor (board and flows view). A regression test guards it.
- **Sharp screens at any zoom:** the board and the flows view kept the world as one GPU layer all the time, so the browser drew the screens once and then only stretched that picture — zoomed in, they were blurry. The layer is now used only while the camera moves (smooth panning and zooming); once it stops, the screens are redrawn at the current zoom, crisp.
- **Zoom in further:** up to 600% (was 300%) — enough to fill a large screen with one screen when presenting (a web page at nearly twice its real size, a phone screen at two and a half).
- **The logo is always the whole wordmark, and white on dark:** the app shows "orbito" in full (top bar, skills map) instead of its "o" alone, and the "o" is no longer a separate logo file. The sign appears on its own only as the browser tab's icon, where the wordmark does not fit (a project that sets its own icon in `index.html` keeps it). The wordmark takes the colour of the text around it, so it turns white on a dark surface; `assets/` has `orbito-wordmark.svg` (dark, for light backgrounds) and `orbito-wordmark-light.svg` (white, for dark ones), and the README shows the white one in GitHub's dark mode.
- **Updates you can trust:**
  - `orbito update` keeps a list of what Orbito installed (`.orbito/managed.json`, with a fingerprint of each item). A skill or agent of yours that has a name Orbito uses is never overwritten (reported instead); an Orbito skill edited in your project is saved to `.orbito/backup/<date>/` before it is replaced; retired skills are removed only if Orbito installed them.
  - Claude is told exactly what the update changes and what it never touches, and to run the whole command when asked to update — never a partial "engine only" update (`orbito-workspace`, `/orbito-update`, the project's `CLAUDE.md`).
- **Your skills, apart from Orbito's:** skills and agents you add appear on the skills map in their own group, "Your skills and agents", instead of under Orbito. Rules for your project go into a skill of your own (or `CLAUDE.md`), never into an Orbito skill, which every update replaces.
- **Audits, one role and consistent names:** the design auditor runs every audit, with fresh eyes — `ux-audit` (new: paths, gaps, stories, words; was the audit half of `ux-review`), `ui-audit` and `accessibility-audit`; designers no longer audit their own work. Deciding on findings, proposed changes and the review with the client is `design-decisions`, run by Orbito with the owner of the work and you. `ux-review` is retired (`orbito update` removes it). Process tables, the lead's routing and the demo use the new names.
- **Audits on Opus:** the design auditor runs on Opus with medium effort (high in the high mode). Sonnet with high effort stays only for the synthetic users, run many at once.
- **Every visual change goes to the design system:** when a screen needs something new or different, Orbito asks whether to change the component, add a variant, or keep a one-off exception — never solved silently in the screen. An exception is marked `// ds-exception: <why>`; `check:ds` then lists it in Health with its reason (rule `ds-exception`) instead of failing.
- **A way back from the skills map and the design-system catalog:** "‹ Back to board" (or to flows) at the top left, Esc, and "Skills" in the top bar works as a toggle.
- **The details panel hides instead of clearing:** its button hides the panel (like the one in the top bar) and keeps the selected screen, so its details come back — before, × cleared the selection and there was no way to get it back from the board.
- **Stable core:** the board, the flows diagram, input, link detection, screen frames and the update are now treated as the stable core: fixes come with tests, behaviour changes need an explicit "Changed" note and a migration.

## 0.9.3 — 2026-10-24
UX review of the viewer itself (notes from use, decided with the `ux-review` competence).
- **Statuses belong to features, not screens:** a change of requirements touches the whole flow, so the status sits on the flow (the lane header on the board, a dot next to the flow in the left panel, the list of features in the details panel). Stored in `.orbito/status.json` under `flow:<page>/<flow>`; old per-screen entries are ignored.
- **Status as a dropdown in place:** a native select where the status is shown — no more menu opening outside the screen (and blocking clicks, which stopped screens from highlighting on hover).
- **Two-way sync:** a status changed on the board writes the file; a status Claude (or you) writes in the file shows on the open board at once, without a reload.
- **One purpose for the right panel — "Details":** with nothing selected, the features of this page with their statuses; with a screen selected, its details (where it leads, by name). View options moved to "View" on the bottom island.
- **Light captions above screens, as in design tools:** the code small and grey on top (with a version's findings), the functional name right over the screen, up to two lines — room for names of up to about six words ("Edit notification options"), the full title on hover; no frame around the card, no status and no ↗ button (a click on a screen already opens the prototype).
- **Screen codes and names, written down:** the `wireframes` skill now says how to name and number screens — the name says what happens, in the users' words; the code is `<AREA>-<NN>` per area of the information architecture (not per feature: one screen often serves several features, and features change), permanent, never renumbered; review versions `PL-02·A`. A team with its own numbering keeps it.
- **Names instead of codes:** flow boxes lead with the screen's name; ways out under a screen are a quiet arrow with a count, and on hover they name where they go — a screen of the same feature by its name, any other way out by the feature it opens ("→ Add a plant").
- **For developers, in the screen details:** where the screen lives in code — the file path (copy it whole), **Show in Explorer / Finder** (the name follows your system), **Open in editor**, and **Copy for Claude** (a reference to the screen to paste into the chat). No HTML/CSS dump: a screen is built from design-system components, which the details already list.
- **Left panel redone after a UX audit:** one chevron icon for every level (pages too) with a proper click area; one row height and indentation with guide lines; names first and codes small and grey on the right (pages, features, screens); a feature's path shown as the line from the flows legend (solid, dashed, dotted), so the only dot left is its status; versions with a branch icon and their state as a label.
- **New model policy** (Sonnet with medium effort gave weak, generic designs in testing):
  - **Sonnet high is the floor**, used only for work that is repeated or run many times in parallel: the design auditor and the synthetic users. Nothing runs on Haiku any more.
  - **Opus medium is the default** for the work itself (business analyst, UI designer).
  - **Opus high for strategic decisions** made once that everything after builds on: Orbito, the UX designer (architecture and flows), the value proposition, look & feel.
  - The **high** mode moves everything to Opus, one effort step up, and the strategic work to very high effort (`xhigh`).
  - A competence can have its own line in the profiles (`<role>/<skill>`), used when Orbito delegates that competence: `ui-designer/look-and-feel` and `business-analyst/value-proposition`. The skills map shows it next to the competence; `orbito models` lists it. A test guards the policy in the shipped profiles. Projects get the new profiles with `orbito update`.
- **Look & feel, reworked after a failed test on a redesign:**
  - asks first **how big the change is** (refresh, redesign or from scratch) and what must stay versus what gets ploughed over; in a full redesign the current page is a source of content and assets, never of layout;
  - sets a **quality bar from references**: the person's examples plus the best current work in the industry, with what to learn from each;
  - **an idea is structure, not decoration**: a device laid over an unchanged layout is rejected (test: remove it — does the design change?), with a worked example;
  - redefines the levels: safe = calm and professionally designed, in between = classic layout with a few deliberate effects, bold = a modern concept on the level of the references;
  - uses the assets well (real photos, an icon with a short text where people scan a list) and adds a last critique pass against the references.
- **Responsive pages, three sizes side by side:** a screen can declare `viewports: ['desktop', 'tablet-web', 'mobile-web']` — one implementation, shown at desktop size on the board and at all sizes next to each other (one scale) in the prototype view. Pages are query containers, so `@container page (…)` rules and `cqi` units adapt them to each width. New built-in viewport `tablet-web`. Landing pages are now one responsive screen instead of separate desktop and phone screens.
- **Web pages behave like a browser window:** `PageScreen` is now exactly the viewport's size and only its content scrolls — on the board and in the prototype — instead of one long static screen. New slots for what stays in place: `top` (header, navigation), `side` (side navigation, filters, a drawer; `sideAt`), `bottom` (sticky actions, a cookie bar), `overlay` (chat button, toast), next to `modal`; `position: sticky` inside the content sticks to the window. The static export stays a real page (the browser scrolls, the bars are sticky). The demo's admin screens use `side` and `top`; the `wireframes` skill and the landing-page process say what goes into the frame and what into the content. **Check your web screens:** a side panel or a header built into the content now scrolls away with it — move it into its slot.
- **Look & feel closes when a direction wins:** as soon as one variant clearly wins (the person picks it, or starts refining only that one), Orbito proposes closing the exploration: with the person's consent it keeps that direction, removes the other variants (their versions and `design-system/variants/` folders) and records the choice in `.orbito/process.md`. Refining then happens in the design system and the real screens (`design-system`, `ui-design`), not inside a variant. While still choosing, feedback changes the variants in place — never more than five open, so the board does not fill up with versions. The UI designer starts only on a closed look & feel; the process tables say so at the decision step.
- **Orbito's logo:** the wordmark "orbito" as a vector in `assets/orbito-wordmark.svg`, heading the README. (0.9.3 also used its "o" alone in the app; 0.9.4 replaces that with the whole wordmark.)

## 0.9.2 — 2026-10-23
- **Skills in three layers:** Orbito (the lead) runs **processes** (`process-new-product`, `process-redesign`, `process-rapid-prototype`, `process-landing-page`), each a table of steps with the role, the competence, the output and where you decide; **roles** (agents) preload their own **competences** (`skills:` in the agent file).
- **New competences:** UX — `information-architecture`, `user-flows`, `wireframes`, `ux-writing`, `ux-review` (from the former `ux-design`); BA — `user-stories` (good-practice stories: INVEST, given/when/then, splitting, definition of ready; checks and completes what you bring), `prototype-scope`, `requirements-sync`; UI — `ui-design` (hi-fi screens).
- **Stories ↔ flows:** the UX designer builds flows from the analyst's stories and links them (`requirements` on a flow, `meta.requirements` on a screen, `requirements/coverage.md`).
- **Skills map** shows the three layers: Orbito, the processes with their steps, the roles with their competences.
- **Five roles:** business analyst, UX designer, UI designer, design auditor, synthetic user. The UX and UI designers build their screens in code themselves (the prototyper role is gone); the copywriter's work is split into `value-proposition` (business analyst: audience, values, proof, personas) and `page-copy` (UX designer: the words of the page, written from it).
- **Rapid prototype = a vertical slice:** the analyst picks the slice from all the context, UX builds the flow and lo-fi screens with copy, a critical UX audit and fixes repeat until clean; UI goes on top only if the person wants it and a look & feel exists. (A narrated demo of the prototype comes later.)
- **Stories stay consistent:** after any approval of flows or screens the analyst shows where they differ from the stories, asks whether to update them, and keeps `requirements/` and the team's tracker (through a connector) in sync.
- **Model modes, personal:** `optimal` (each role on the model and effort its work needs — fewer tokens) or `high` (the strongest model almost everywhere, high effort where the work is strategic). Two profiles in `.orbito/models.json` (Orbito's). Each person picks their own: `npx orbito models high` saves it in `.orbito/settings.local.json` (git-ignored); `--team` sets the team's default in `.orbito/settings.json`; the `ORBITO_MODELS` environment variable wins over both. Agent files never change — Orbito passes the profile's model and effort each time it calls an agent. Orbito asks at the kickoff; the top bar shows the mode next to "Skills" (hover: what it means, whose setting it is, how to switch); the skills map shows each role's model and effort in that mode.
- **Personal files stay personal:** `.orbito/settings.local.json` and `feedback.md` are in `.gitignore` (`orbito update` adds them to older projects), so one person's settings or feedback notes never reach the team's repository.
- The skills map refreshes by itself when skills, agents or the model mode change.
- Removed and replaced by the above: skills `ux-design`, `requirements`, `rapid-prototyping`, `landing-page`, `sales-copy`; agents `prototyper`, `copywriter` (`orbito update` removes them).
